# SEO分析から改善・新規制作への接続

この文書は2026-11-28の実装仕様。配備・有効化・実行成功は別途受領情報で確認する。

## 起動と担当

macproの既存編集runnerを唯一の実行主体とする。5分ごとの起動で期限・状態をプログラムが確認し、
日次収集はJST08時以降に1日1回、通常制作は既存の金曜09時開始・金曜〜木曜の制作期に従う。
旧SEO supervisor、別AI manager、Codex側の定期監視を追加・再開しない。

1. **プログラム**：GA4・GSCの収集受領情報、日付・対象期間・snapshot hashを照合する。欠測は0にしない。
2. **プログラム**：既存記事との重複、改善候補、未公開枠、共有予算を確認する。
3. **AI**：検証済み分析資料を使い、季節の悩み・ノウハウ・商品やブランド比較から企画を選ぶ。
4. **プログラム**：商品・型番・色サイズ・画像・利用条件・購入先・出典を確認してから既存制作工程へ渡す。
5. **既存AI工程**：執筆仕様に沿う本文、Gemini校正、独立QA・Claude審査・必要な上位QAを行う。
6. **プログラム＋本人**：Slackへ対象版の本文・画像・購入リンクを提示し、本人の記事承認を待つ。
7. **プログラム**：承認版だけ公開し、公開後チェック・サイトマップ・GSC URL検査と既存再確認を行う。
8. **AI＋本人＋プログラム**：SNS案を別途作成・審査・本人承認し、既存Buffer経路で予約・投稿を照合する。

記事32calls・制作期128calls・通常週3本・新規未公開3件を維持する。過去の結果不明は枠から消さない。
到達時は品質を緩和せず保留する。API実測token、概算USD、実請求不明、Codex側の取得不能量を分ける。

## 企画出力の限定回復

受信済みで利用量が確定し、全候補が形式違反だった場合だけ、同じ制作期予算内で追加企画を1回認める。
旧marker・応答artifact・入力contextのhashと履歴を残し、新しい入力で企画する。旧案を勝手に補完して採用しない。
再失敗、通信結果不明、拒否、予算・品質・需要根拠不足はこの回復対象ではない。
同じ状態の再起動では追加AIを呼ばない。既存の11/20専用回復と混用しない。

## 既存記事の改善準備

最初は制作期ごと最大1件。新規週3本とは別計数だが、共有制作期予算は同じ。
最新分析・公開本文・商品snapshot・出典を照合し、既存の改訂工程へ渡す。
平均掲載順位1〜3位やクリック上位記事は自動の一般SEO改稿から保護する。
明示的に依頼された事実訂正を妨げるルールにはしない。
既存改訂待ち、公開ベースの変化、商品未確認、結果不明があれば対象を保留し、無関係な新規企画は止めない。

表示回数と平均順位だけで「タイトルと検索意図が不一致」「CTR低下の原因」と断定しない。
数値は改善仮説の入口とし、本文・検索意図・商品・リンクの確認を修正仕様にする。
新しい事実・使用体験・商品差替えを分析値から生成しない。記事とSNSの本人承認は独立したままにする。

通常の分析改訂だけは、現在の公開本文・FAQを最大12,000文字／32KiBの参照としてwriterに渡す。
公開ベースのhash、秘密値検査、医療リスク検査、fresh source検査を通し、旧本文を出典・命令として扱わない。
大きすぎる本文や医療リスクは上位編集を要する保留にする。旧手動改訂の本文非送信は維持する。
参照は既存stage journal・共有予算内のwriter入力だけとし、polish/finalへ旧全文を反復送信しない。

## 参考資料の取り込み範囲

XtomSEO資料の「勝っている記事を守る」「既存記事改善」「検索意図と本文の約束を合わせる」
「週次は重要な3件へ絞る」を採用する。一朝のデモや宣伝グラフを改善実績とは扱わない。
日本向け検索ボリューム・外部競合・トレンドが未接続なら欠測とし、値や順位向上を作らない。
日々の収集・差分・期限・重複排除にAIを使わず、本文変更のない監視でモデルを反復起動しない。
