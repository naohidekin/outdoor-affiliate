# SEO分析から改善・新規制作への接続

この文書は2026-11-28の実装仕様。配備・有効化・実行成功は別途受領情報で確認する。

## 起動と担当

macproの既存編集runnerを唯一の実行主体とする。5分ごとの起動で期限・状態をプログラムが確認し、
日次収集はJST08時以降に1日1回、通常制作は既存の金曜09時開始・金曜〜木曜の制作期に従う。
旧SEO supervisor、別AI manager、Codex側の定期監視を追加・再開しない。

1. **プログラム**：GA4・GSCの収集受領情報、日付・対象期間・snapshot hashを照合する。欠測は0にしない。
2. **プログラム**：既存記事との重複、改善候補、未公開枠、共有予算を確認する。
3. **AI**：検証済み分析資料を使い、季節の悩み・ノウハウ・商品やブランド比較から企画を選ぶ。
4. **プログラム**：商品・型番・色サイズ・画像・利用条件・購入先・出典を確認してから既存制作工程へ渡す。
5. **既存AI工程**：執筆仕様に沿う本文、Gemini校正、独立QA・Claude審査・必要な上位QAを行う。
6. **プログラム＋本人**：Slackへ対象版の本文・画像・購入リンクを提示し、本人の記事承認を待つ。
7. **プログラム**：承認版だけ公開し、公開後チェック・サイトマップ・GSC URL検査と既存再確認を行う。
8. **AI＋本人＋プログラム**：SNS案を別途作成・審査・本人承認し、既存Buffer経路で予約・投稿を照合する。

記事32calls・制作期128calls・通常週3本・新規未公開3件を維持する。過去の結果不明は枠から消さない。
到達時は品質を緩和せず保留する。API実測token、概算USD、実請求不明、Codex側の取得不能量を分ける。

## 企画出力の限定回復

受信済みで利用量が確定し、全候補が形式違反だった場合だけ、同じ制作期予算内で追加企画を1回認める。
旧marker・応答artifact・入力contextのhashと履歴を残し、新しい入力で企画する。旧案を勝手に補完して採用しない。
再失敗、通信結果不明、拒否、予算・品質・需要根拠不足はこの回復対象ではない。
同じ状態の再起動では追加AIを呼ばない。既存の11/20専用回復と混用しない。

## 既存記事の改善準備

最初は制作期ごと最大1件。新規週3本とは別計数だが、共有制作期予算は同じ。
最新分析・公開本文・商品snapshot・出典を照合し、既存の改訂工程へ渡す。
平均掲載順位1〜3位やクリック上位記事は自動の一般SEO改稿から保護する。
明示的に依頼された事実訂正を妨げるルールにはしない。
既存改訂待ち、公開ベースの変化、商品未確認、結果不明があれば対象を保留し、無関係な新規企画は止めない。

表示回数と平均順位だけで「タイトルと検索意図が不一致」「CTR低下の原因」と断定しない。
数値は改善仮説の入口とし、本文・検索意図・商品・リンクの確認を修正仕様にする。
新しい事実・使用体験・商品差替えを分析値から生成しない。記事とSNSの本人承認は独立したままにする。

通常の分析改訂だけは、現在の公開本文・FAQを最大12,000文字／32KiBの参照としてwriterに渡す。
公開ベースのhash、秘密値検査、医療リスク検査、fresh source検査を通し、旧本文を出典・命令として扱わない。
大きすぎる本文や医療リスクは上位編集を要する保留にする。旧手動改訂の本文非送信は維持する。
参照は既存stage journal・共有予算内のwriter入力だけとし、polish/finalへ旧全文を反復送信しない。

## 参考資料の取り込み範囲

XtomSEO資料の「勝っている記事を守る」「既存記事改善」「検索意図と本文の約束を合わせる」
「週次は重要な3件へ絞る」を採用する。一朝のデモや宣伝グラフを改善実績とは扱わない。
日本向け検索ボリューム・外部競合・トレンドが未接続なら欠測とし、値や順位向上を作らない。
日々の収集・差分・期限・重複排除にAIを使わず、本文変更のない監視でモデルを反復起動しない。

## 版ごとの循環確認と停止原因の修復

GA4のページ一覧はGSCの改善候補を優先して既存30件上限へ投影する。件数制限で落ちたページを未取得や0として扱わない。
private query/page行はローカルで既定の分類語へ集約し、観測サンプルとしてだけ扱う。原検索語、検索語のhash、検索意図の断定をAIへ渡さない。
外部SERP、検索市場全体、CTRの因果は、この観測サンプルから補完しない。

既存記事改善の旧no-selection保留は削除しない。本人が修復を指定した場合だけ、旧resultのhashと新分析・実装・本人指示を束縛し、
同じ制作期で一度だけ追加の選定を認める。source失敗、結果不明、予算到達、改訂待ちはこの回復権の対象外。
通常も回復時も商品調査の鮮度は調査完了時刻で判定する。記事32calls・期128callsと改訂1件/期は据え置く。

`independentReviewEnabled`を明示有効化した場合、改訂・商品訂正の審査後に、既存のhost-pinned Astra CLIで独立品質確認を行う。
対象版ごと1試行、180秒、同じ記事・制作期予算から保守的に出力16,384 tokensを予約する。
CLI側の生成token上限は強制できないため、その予約値を実際の強制上限と表示しない。取得したusageで精算し、欠測は未知の予約として保持する。
記事・SNSの本人承認には一切代用しない。失敗・結果不明・予算到達で品質を下げず保留し、同じ版を自動で再審査しない。

`check-corrected`は共有商品変更の前に、影響する公開本文・FAQの旧ASIN・URL・文脈付きサイズ表記を読み取り専用で照合する。
訂正待ちはpublish effectの予約前で止める。接続不能と訂正待ちは別状態にする。
保留の再照合は関連公開記録の変化または30分経過時のみ。成功結果は公開許可のキャッシュにせず、実公開時も独立に再確認する。

`seo-feedback/latest.json`が企画・承認・公開・公開後監査・サイトマップ/GSC検査・再分析の版別証拠を結ぶ。
同一証拠のtickはAIも同じファイルの書き換えも行わない。次の企画へ渡すのは最大3件の短い観測結果だけとする。
`analytics/seo/latest.json`は現在の数値レポート本文で、週次/月次Slackにも循環確認の件数を載せる。
再分析実行と公開後の効果計測、Google登録とサイトマップ掲載、数値変化と因果効果は区別する。
新規記事の公開前baseline欠落、公開日を含む混合期間、GSC確定待ちは「改善実績」にしない。

## 2026-11-28の本人指定による不足2案の追加調査

11/27期の既知適格1案は再生成せず固定する。`research_pool_completion`は旧marker・選定receipt・入力・
受信済みraw artifact・利用量のSHAと、今回の本人指示を照合し、追加企画権をAPI前に一度だけ消費する。
追加Claude企画は1回、32calls/記事・128calls/制作期の既存枠内。通信結果不明や不合格で権利を戻さない。
残り2案も通常の需要・重複・一次資料・商品照合を通し、通常の3案poolとして既存producerへ渡す。
外部人気、固有モデル対の需要、GSCの関連ページ実績を混同しない。通常40groupの外を調べる場合も、
privateの既取得query行をcontrolled facetへ再集約し、原検索語をモデルへ送らない。

購入先の選択肢が変わった場合、旧variantを未確認のまま合格にしない。新候補は私的snapshotとfresh sourceへ束縛し、
商品・サイズ差と既存記事への共有影響をSlackで確認できる形にする。通常の独立QAと本人承認を維持する。
上限により後続制作が待つ場合、購入先訂正もpoolで保持し、後続job生成と同じtransactionで付与する。
この操作自体は共有商品の公開更新、記事承認、SNS承認、Buffer予約を行わない。

### 2026-11-28 実運転での追補

- 商品訂正の公開前確認が依存待ちの場合、同じ30分以内の再確認を抑制し、その原因を直す既存記事改稿を先へ進める。公開許可のキャッシュは作らず、関連公開版の変化で待機キャッシュを無効化する。
- 再分析は新記事の公開後実数と、改稿の前後比較を区別する。新記事の公開前を0に補完しない。改稿は選定時に保存した同一条件・同一長さのページ実測期間を基準にし、公開日を含む期間から効果を捏造しない。
- 公開版の再分析は最大1000件の状態を対象URLごとに元計測行から再サニタイズする。保存レポートはエラー・待機を優先して最大10件、次回企画入力は実測済みを優先して最大3件とし、企画用30件制限の外にある記事を永久に欠測扱いにせず、企画の保護条件は変えない。
- 実際のソース確認失敗は保留のまま記録する。受領情報の削除や試行枠の初期化による再実行はしない。

表示確認の対象外は固定された静的な表示設定と実DOMの両方で証明する。記事に元からない医師助言欄を追加・削除して通すことはせず、対象外も記事版に結び付け、公開前と公開後に照合する。表示確認だけの修復では、成功済み本文・校正の同一入力/出力を保存済み応答から再利用し、違いがあればモデルを再呼出しせず保留する。

### 独立審査へ渡す検査証拠

改稿・共有商品訂正の独立審査では、商品・購入先・画像・医療リスク・PC/スマートフォン表示の実検査を、記事版と出典へ結んだ変更不能の受領情報に保存する。内部リンク先の公開内容と商品写真の構成情報を短く投影し、HTML・画面保存先・認証情報は送らない。
プログラムは表示、クリック先、画像バイト列とSHA、未確認価格・評価・在庫の表示を検査し、AIは本文と根拠、商品・販売先・画像の意味の整合性を審査する。AIに表示検査を重ねさせず、視覚確認を行ったとは記録しない。
証拠欠落・不一致・入力上限到達は有料審査前に保留する。同じ記事版の独立審査は1試行のままであり、証拠投影の修正で失敗履歴や利用量を初期化しない。記事とSNSの本人対象版承認は別に維持する。
