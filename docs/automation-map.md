- **実際に毎朝10:00に稼働している本物の実行環境は MacBook Air の `~/dev/outdoor-affiliate`**

**実施した対処（2026-08-01）**:
- Proの8ジョブを `launchctl bootout` で停止し、plistを `~/launchagents-backup-20260801/` へ退避（削除ではない）
- Proのデスクトップにあった抜け殻フォルダを `~/icloud-shell-backup-20260801/` へ退避
- Proの `~/dev/outdoor-affiliate/.env.local` にAirの完全版キーを配置（予備＋SSH経由の同期経路確保）
- Pro側で `npm run db:sync -- --dry-run` の動作確認済み（categories 21 / products 377 / articles 117）
  ※ Pro側でnpmを使う場合は `export PATH=/usr/local/bin:$PATH` が必要

**運用上の結論**:
- **定時実行の正本は Air の `~/dev/outdoor-affiliate` のみ**。Proは手動実行できる予備環境という位置づけ

## 複数マシンで触るときの同期手順（2026-08-01 追記）

`sync-to-supabase.js` は既定で「Supabase → ローカルJSON書き戻し（auto-pull）」を先に実行する。
このとき記事・商品が `updated_at` 順に並べ替えられるため、**git上の並びと食い違って
全行が差分として出る**（実害はないが、次回の `git pull` が
"Your local changes would be overwritten" で止まる原因になる）。

### 推奨フロー

リモート（Claude Code / Web）で編集 → Macに取り込んで本番反映する場合:

```bash
cd ~/dev/outdoor-affiliate
git pull                                    # 先にgitを最新にする
node scripts/sync-to-supabase.js --no-pull  # 書き戻しをせずSupabaseへ反映
```

`--no-pull`（または `SKIP_AUTO_PULL=1`）を付ければローカルJSONは書き換わらず、
gitの状態がきれいなまま保たれる。

### auto-pull を使うべきケース

**管理画面（/admin）でSupabase側を直接編集した直後**は auto-pull が必要。
その編集はgitに存在しないため、`--no-pull` で同期するとローカル（＝git）の内容で
上書きされて失われる。この場合は素直に auto-pull ありで実行し、
書き戻しで出た差分はコミットしてgitに戻す。

### 並び替え差分が出てしまったときの片付け

書き戻し差分は「並び替えのみ」であることがほとんど（追加行数と削除行数がほぼ同数なら並び替え）。
記事の欠落がないことを確認してから捨てる:

```bash
git stash push -m "sync-writeback" data/articles.json data/products.json
node -e 'const a=require("./data/articles.json");console.log("記事数",a.length,
  "／公開",a.filter(x=>x.status==="published").length)'
git stash drop   # 欠落がなければ捨てる
```

### 定時パイプラインの自動コミット（2026-08-01 修正）

`article-orchestrate.js`（日次）と `orchestrate.js`（週次）は実行後に
`data/` を自動コミット＆プッシュする。以前は commit 直後に push していたため、
リモートが先に進んでいると push が弾かれ、**ローカルにコミットだけが取り残された**。
翌日以降 `git pull` が divergent branches で止まり、手作業の復旧が必要になっていた。

現在は `commit → git pull --rebase → push` の順に修正済み。競合時は
`rebase --abort` して中断しエラーを返す（データJSONを機械的に片側へ倒すと
記事・商品が丸ごと消えるため、人が中身を見て判断する）。

**パイプラインが「rebase失敗」で終了していたら**、Mac上で状況を確認して手動で解決する:

```bash
cd ~/dev/outdoor-affiliate
git log --oneline origin/main..HEAD   # ローカルにだけあるコミット
git log --oneline HEAD..origin/main   # リモートにだけあるコミット
git status --short
```

そのうえで `git pull --rebase` を実行し、競合したファイルは中身を見て解決する。
`git checkout --ours/--theirs` は使わない（JSONが片側に倒れてデータが消える）。

   push待ちとして保持する。価格やURLだけ書き換えたスクリプトは、次の

   **データを直接書き換えるスクリプトは必ず `updatedAt` を進める。**

2. **同期は `npm run db:sync -- --no-pull` を使う**
   まだDBに無いローカルの修正を auto-pull が旧値で潰す。二重の保険として付ける。

3. **楽天APIはIPv4のIP許可リスト。IPv6回線だと永久に一致しない**
   `curl -s ifconfig.me` がIPv6を返す環境では、その値を登録しても無意味。
   `curl -4 -s ifconfig.me` でIPv4を確認して登録する。スクリプト側は
   `dns.setDefaultResultOrder("ipv4first")` で固定済み。
   許可IPはCIDR表記も使える（`143.189.126.0/24` 等）。移動のたびに追記が必要。

4. **同一ASINを複数商品が共有している**
   おにやんま君（`chair-006` / `insect-repellent-001`）、
   スランバーシュラフ・2（`sb-kids-003` / `sb-budget-002`）など。
   片方だけ更新すると価格が食い違う。`find` ではなく `filter` で全件そろえる。

5. **低信頼の提案は半数近くが別商品**
   楽天で低13件中6件、Amazonで低10件中3件が誤り（WAVE 2→WAVE 3、
   本体→ソーラーパネルセット、別ブランドなど）。
   **`--apply` は高・中のみ。低は目視して `--only` で通す。**

6. **Amazonの検索結果は実行ごとに揺らぐ**
   同じ商品・同じキーワードでも、順位変動で別ASINが返る。
   「一致率100%」が毎回出るとは限らない。適用後の再検証が要る。

## 2026-08-08: 世代・グレード違いの取り違えを塞ぐ

8/6の作業で残った「低信頼度」の候補を精査したところ、**同じ原因で複数件が別商品を
掴んでいた**。原因はキーワード生成の共通化にあった。

### 何が起きていたか

`sanitizeKeyword` は1文字の語を落とす。これは**楽天APIが1文字語を含むキーワードを
400で拒否する**ための処理で、Amazonには不要な制約だった。共通モジュール化のときに
一緒に持ち込んだ結果、世代番号が検索語から消えていた。

| 商品 | 実際に投げた検索語 | 掴んだ商品 |
|---|---|---|
| EcoFlow WAVE **2** | `EcoFlow WAVE` | WAVE **3** |
| EcoFlow DELTA **3** Plus | `EcoFlow DELTA Plus` | ソーラーパネル同梱セット |

さらに厄介なのは、キーワードを直しても**一致率は100%のまま**だったこと。
`tokenOverlap` は2文字未満の語を落とすうえ部分一致なので、商品名の「2」が
候補側の「【2026年新型】」に当たってしまう。つまり修正後は「中」に昇格して
**目視なしで自動適用される**ところだった。

### 3か所で塞いだ

1. `sanitizeKeyword(s, { minTokenLength })` — Amazon側は `1` を渡して世代番号を残す
2. `generationMismatch(productName, itemName)` — 商品名の数字列を**完全一致**で
   突き合わせ、候補側に無ければ低へ降格。「2026年」への部分一致を塞ぐ
3. `sizeToken` に `ST` を追加 — ST/LX は数字が無く世代判定に乗らない。
   実際に `tent-duo-001`（ツーリングドーム**LX**）に**ST**のASINが付いていた

### `--ids` を追加した

`--only` は「反映する商品」の指定であって、調べる商品の指定ではない。
**既に `/dp/` が入っているが中身が別商品**というケースは通常の対象条件
（検索URL／未設定）に入らず、調べ直す手段が無かった。

```bash
node scripts/fix-amazon-search-links.mjs --ids tent-duo-001,tent-003 --explain
```

## 2026-08-11: 価格監査でリンクの取り違えが芋づる式に出た

登録価格を実売と突き合わせる `scripts/audit-prices.mjs` を作ったところ、

### 型番一致「高」は安全ではなかった

一番の収穫はこれ。型番が一致すれば取り違えないという前提で
信頼度「高」を自動適用していたが、**穴が2つあった**。

1. **前方一致が数字の伸びを許していた**
   `REF-025` が `REF-0254` に一致し、サーモスのソフトクーラーが
   ペット用ブラシを指していた。カラー違い（`BD-347` と `BD-347BR`）を
   許すための仕組みが、そのまま抜け道になっていた。
   英字接尾辞だけを許す `modelsMatch` に修正。

2. **抽出が長い品番の一部を切り出していた**
   シャツの品番 `LFTG-BD-190` から `BD-190` が取れ、BUNDOKの
   シェラカップ `BD-190` と**完全一致**した。前方一致を直しても
   救えなかったのはこのため。
   直前の文字を見て弾く方式は `YEC-M03` のような多段型番を
   壊す回帰が出たので、**ハイフンの塊をまるごと1つの型番として扱う**

同じロジックが楽天版に2か所・Amazon版に1か所コピーされていたので、

**型番だけでは原理的に守れない**ことも分かった。BUNDOKの `BD-190` は

「600ml が候補に無い」「登録価格の4492%」の2つのガードが効いて

### ブランドを独立した軸にした

本物の誤リンク4件は**すべてブランドが違っていた**（ロゴス→LACITA /
DARCHE→XiaZ / ファイヤーサイド→Redecker / スノーピーク→キャプテンスタッグ）。
ならば一致率とは別に「ブランドが合っているか」を見るのが素直で、
一致率が0%でもブランドが合えば誤リンクとは断定しない設計にした。

- `data/brand-aliases.json` … 表記対応表（約110行）
- `src/lib/product-match.mjs` … `brandVariants` / `brandMatches` / `normalizeBrands`
- `scripts/test-link-verify-cases.mjs` … 実際に出た16件を実データで固定した回帰テスト

無関係な商品ペア2289件で誤ってブランド一致するのは1件（0.04%）。

`brand` フィールドは店名や飾りが混ざる（「Mystic Ridge 楽天市場店」
「アウトドアチェア【ポンコタン】」）ため、塊に割って店舗接尾辞を落とす。
ただし**一般名詞だけの候補は捨てる**。「アウトドアチェア」を候補に
残すと、その語を含むタイトルは何でもブランド一致になってしまう。
ブランド一致は疑いを**外す**側に効くので、緩めると誤リンクを見逃す。

### 価格が合っている誤リンクを、監査が丸ごと見逃していた（重要）

`audit-prices.mjs` は「別商品を指している疑い」を、価格が20%以上ずれた
ものの中から絞り込んでいた。そのため**「別商品なのに価格はたまたま
合っている」ケースが画面から消えていた**。

`tarp-007` がまさにそれで、リンク先の LACITA のランタンが偶然 ¥10,800 と
登録価格と同額だったため、レポートJSONに `wrongLink: true` が入っている
のに画面には「疑い0件」と出ていた。過去の全件監査にも効いていた可能性が
あるので、修正後に全件を回し直すこと。

### 直した3件

| id | 症状 | 対応 |
|---|---|---|
| `fire-blower-fireside80` | Redecker の火吹き棒を指す | `B073SB9PGZ` に差し替え |
| `tarp-008` DARCHE | XiaZ の日除けシェードを指す | Amazonリンク削除＋除外登録 |
| `tarp-007` ロゴス | LACITA のランタンを指す | `B08L5ZQMR1` に差し替え |

`tarp-007` は自動照合の価格ゲートに落ちた（Amazon ¥5,980 が登録 ¥10,800 の
55%）。だがタイトルの `74175042` は LOGOS の品番で、登録済みの楽天リンク
`7dials/7d74175042` と同じ番号だった。品番が一致している以上、価格差は
モールによる売値の違いであって別商品ではない。

ここでゲートを緩めるのは誤り。緩めれば全商品に効いて、付属品や別グレードを
掴む事故が戻る。代わりに `scripts/set-amazon-link.mjs` を作り、**人間の確認を
ゲートの代わりに置く**経路を用意した。1件ずつしか効かず、書き込む前に
実物のタイトル・価格・ブランド一致・一致率と「自動照合ならここで止まる」
理由を必ず表示する。

### 落とし穴（15〜17番目）

15. **`--only` で価格ゲートは通せない**
    価格ゲートは候補の選抜段階で効き、落ちたものは提案自体が作られない。
    `--only` はできあがった提案から選ぶだけなので、順番として届かない。
    説明に「低も反映」とあるのを拡大解釈して、通ると誤案内した。
    目視で確定したASINは `set-amazon-link.mjs` で入れる。

16. **値段が合っていることは、同じ商品である証拠にならない**
    上記の監査バグの本質。リンクの正誤は価格と独立に判定する。

17. **`getItems` は配列ではなく `{ items, errors }` を返す**
    配列と思い込んで `items[0]` を見たため `undefined` になり、正常な
    ASINにも「Amazonで引けません」と表示していた。Amazon側の問題だと
    誤診し、原因の切り分けに時間を使った。**APIが返すエラーを握り潰さない**
    （`errors` を表示していれば即座に分かった）。
    素で問い合わせる `scripts/lookup-amazon.mjs` を用意した。
    `node -e` で書くと `loadEnv()` を忘れて「認証情報がありません」に
    化けるので、調査もスクリプトに置く。

### 判断を保留した項目

- `tarp-007` の登録価格 ¥10,800 は、いまどちらのモールの実売でもない
  （Amazon ¥5,980 / 楽天 ¥11,990）。楽天店が定価に近く Amazon が半額という
  モール差で、異常ではない。商品カードは1価格しか出せないので要判断。
  `audit-prices --apply` は両モール一致時しか直さないため自動では動かない
- `fan-socool`（ASIN `B0C4KG77YJ`、30日15クリックで最多）は目視待ち
- `tent-009` は登録ブランドが ESTOAH.home でリンク先はアイモニカ。
  表記ゆれではなく本当に別の出品者なので疑いに残している
